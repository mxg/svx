Pipelined Testbenches
---------------------

Pipelines are constructed of stages, where each stage operates
independently of and thus concurrently with other stages. Each stage
except for the last one sends instructions and data to its adjacent
downstream stage. Classic UVM testbenches are not geared toward
stages.  Instead, they send stimuli to a device and await a
response. Sequencers serve as arbiters, controlling traffic from
concurrent traffic streams generated by sequences.

However, using classes already in UVM we can construct some new
classes that support construction of pipelined testbenches.  The key
idea is that each stage looks like a driver to its upstream neighbor
and looks like a sequencer to its downstream neighbor.  SVX provides
two classes to build these sorts of components.  One is
pipe_stage_base#() which is derived from uvm_component. Like a
sequencer, is parameterized with the type of the sequence item that
flows through it. The other class is pipe_stage#() which is also
parameterized with the sequence item type.  The reason of having two
classes instead of a single pipe stage base class is so we can
construct first and last stages.  The first stage in a pipeline does
not accept an item from upstream, and the last stage does not send an
item downstream.

Pipe_stage_base has a seq_item_export for sending an item downstream.
Pipe_stage has a seq_item port for accepting an item from upstream. To
construct the pipeline during the build_phase you connect the
seq_item_port for each stage to the seq_item_export of its upstream
neighbor.

Pipe_stage spawns two threads -- enqueue_items() and dequeue_items().
Enqueue_items() gets the next sequence item from its upstream neighbor
then puts it in internal fifo. Dequeue_items() pulls the next item
from the internal fifo and processes it.  Processing includes any
arbitrary functionality.  However, at some point it must send an item
downstream.  The item can be the same item that it received from
upstream or a new item.

The pipeline stages use an agreement to determine when it's time top
shutdown.  The pipe_stage classes are hardwired to use an agreement
named "pipeline_done".  The girtual funftion pipe_stage::is_idle()
identifies when it's OK to allow a shutdown.  Derived pipeline stages
can override this function to change the criteria for allowing
shutdown.

The example uvm/examples/pipeline demonstrates how to construct a
simple pipeline using pipe_stage_base and pipe_stage classes.
